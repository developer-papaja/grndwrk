It should be possible to say that the stories, and everything else in the map, are saved to a database instead of as files in the project. A team with many apps and systems wants a perspective over all of them, rather than one map per repo.

This goes against the first principle (lives in the project: no accounts, no cloud, no database, `.grndwrk/` is the source of truth). Two needs may be hiding in it, and they need different things:

- **One view over many projects.** This could be had without a database: a grndwrk that reads the `.grndwrk/` folders of several repos at once (a workspace listing them), with an overview across them: questions, gaps, focus, stories done per app. Each map stays in its repo and in git.
- **The map living somewhere other than a repo.** For systems the team does not build in a repo of its own, or people who never open one. That really is a store of its own: a backend behind the same file layout (`NodeStore` and the others would talk to it instead of `src/store/fs.ts`), with accounts, hosting and someone to run it.

The shared server idea (n_0fe7zi) ended in the relay, which closed that gap without moving the map.

## Direction (2026-11-16)

An option chosen at `init`, next to new or existing: where the map is kept. Files in the repo stay the default.

Claude's proposal, not decided, updated after the answers in the thread:

- **Two choices, not three:** files in git (default), or the team's shared store. A database on one machine gives nothing files do not already give, and loses the diffs and the merges.
- **The shared store is the source of truth, with a page on top.** Under the team's own domain, with a login, so people help without having the project, and systems without a repo get a map too. It holds the overview across apps, the thoughts searchable and linked across apps, and personas, segments and design principles defined once for every app. Hosted by the team: on Cloudflare like the relay, or on its own server or database (Postgres or similar). A hosted grndwrk service last.
- **The team shapes it.** Views (filters, overviews, boards) saved in the store for everyone, not per browser, and the data readable from outside through a documented API or export, for the team's own pages and reports. Its shapes are the files' shapes.
- **A system without a repo** keeps its map only in the store, edited on the page, or in a repo made just for the map so an agent can work on it. Both are allowed.
- **The agent keeps working on files.** The commands stay in each repo. Every command and the map's rules read and write `.grndwrk/` as files, and that is why grndwrk works with any agent without an API key. With a shared store, `.grndwrk/` becomes a working copy: grndwrk fetches from the store at start and on changes, and sends what the agent or the map wrote (the watcher sees it already). The layout already makes each new thing a new file, so two people rarely touch the same record, which is what makes syncing simple too.
- **Efficiency.** The store layer reads the whole folder on each request today (`NodeStore.read`, no cache), which is fine for one map of a few hundred files. A view across many apps would need an index kept in memory and updated from the watcher, whether the source is files or a database. The agent's side is where a database could do better: asking for "open questions on this screen" instead of reading the folder costs fewer tokens. That could come later as `grndwrk` commands or an MCP server over the same data, without the agent losing the files.
