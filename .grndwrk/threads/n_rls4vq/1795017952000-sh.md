Built. `ships:` in project.md says what a release is: `versions`, `deploys` (a day something went live, named by its date, one file per day) or `not yet`. Without it, `/release` recommends one from what the project shows, with its reasons, asks on a "How does this project ship?" question, and writes your answer. The first run fills in the history instead of one baseline: a release per version tag, per change of the declared version when there are no tags, or per week of commits for deploys, from when the map starts. Only production counts; packages versioned on their own get their package in the name.

The cases came from looking at all sixteen grndwrk projects on this Mac: versions with tags, versions in a file without tags, deploys tagged by the deploy itself (over a thousand build-number tags), deploys on push without versions, and projects not shipped yet. This repo now says `ships: versions`. The Releases tab says how the project ships.

To test:
1. In a project that deploys on push and has no `ships:`, run `/release`. Your agent recommends Deploys with its reasons, and the question shows in the Inbox. Answer it.
2. Run `/release` again: it proposes one release per week of history since the map started, then today's deploy by its date, and writes them only after you say yes.
3. In a versioned app without tags, run `/release`: it recommends Versions and builds the history from the commits that changed `versionName`.
4. Open Deliverables, Releases: the line at the top says how the project ships. [agent: tried in this repo's map in the browser]
