Security review of the staging relay, focused on what it adds: the relay serving a script, CORS for one site, a browser joining and keeping keys, and grndwrk taking its comments. Looked at from anyone on the staging site, any other website, a script on the staging site, a relay that misbehaves, and an invited colleague.

Holds:
- Only pages on the named site get the button from the relay, and the button runs only on that site; production and other sites get nothing.
- Another website cannot read the relay's answers or send signed requests: CORS is given to the site only, on what a phone may ask only, never the team's paths.
- Nothing the relay holds can be read by it, as before; a browser's comments are sealed and signed as a phone's.
- An invited browser can do exactly what an invited phone can, no more.
- The mailbox's id is now public (it is in the script), which opens no new way in: joining needs the invite's secret, sending needs a key the team allowed, and anyone could already reach the relay with made-up ids.

Fixed in the review:
- The site the relay reports is checked to be an https address before the terminal prints it or the map shows it, so a relay that misbehaves cannot put control characters in the terminal or a misleading address in the map.
- The button's test card can no longer call its old local paths when it runs through the relay.

Accepted, by design:
- A script on the staging site (its own code, or anything it loads) sees an invite while it is pasted. Someone joining with a stolen invite shows other digits than the colleague's, so the map's Allow stops it, as for a phone.
- Such a script can use the browser's keys while the page is open, to send comments as that colleague; it cannot take the keys away. Taking the browser out in Colleagues ends it.

Still open, as before: rate limiting in front of the relay on Cloudflare.
