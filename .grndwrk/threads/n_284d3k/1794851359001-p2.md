That changes step 2 of the plan: the store is not one service grndwrk ships, but a small protocol any backend can speak, with ready-made kits.

- **The store protocol.** A handful of HTTP calls over the same files: list what changed since a version, read a file, write a file if its version still matches, delete one, and a stream (or a poll) of changes. Pictures as plain uploads. Login stays the host's business: grndwrk sends a token the host hands out, the page uses whatever login the host has. Written down in `docs/store-protocol.md`, short enough to implement in an afternoon.
- **A check anyone can run.** `grndwrk store check <url>` runs the protocol's tests against a store and says what fails, so a team's own version is known to work before anyone relies on it.
- **Kits, each a folder to copy:** Cloudflare (the reference, deployed like the relay), Firebase (Cloud Functions over Firestore and Storage, with security rules, set up with `firebase deploy` in the team's own project), and PHP (one small app over MySQL or SQLite, for any PHP host). Each passes the check.
- **In grndwrk:** `init` asks where the map is kept, and for a store only its address and a token. Nothing in grndwrk knows which kit is behind it.

Steps 1 and 3 to 6 stay as they were; they talk only to the protocol, so the page, the overview, views and the API work on every kit.
